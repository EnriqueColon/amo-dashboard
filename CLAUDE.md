# AMO Dashboard

Miami-Dade Assignment-of-Mortgage tracking dashboard. Stack: React/Vite client (`client/`), Express + better-sqlite3 server (`server/`), Python collector pipeline (`collector/`). SQLite DB `miami_dade_amo.db` (gitignored).

**Before doing anything else, read [SESSION_LOG.md](SESSION_LOG.md)** — it has the current state of in-progress work, recent findings, and open threads. It's kept dense on purpose; read it instead of asking the user to re-explain where things left off. Append a new dated entry there at the end of any substantive session (concise — facts, not transcript).

## Closing a session — two files, always

1. **[SESSION_LOG.md](SESSION_LOG.md)** — append a dated entry. Dense, facts only.
2. **[docs/CONFLUENCE_AMO_DASHBOARD.md](docs/CONFLUENCE_AMO_DASHBOARD.md)** — the Confluence page, and the one document a non-developer reads. It must never go stale. Update whichever sections the session's work affects (description, how-to-use, architecture, developer maintenance/runbooks), **always re-check section 7 "Current status"** (production numbers, component status table, known gaps, risk register), and bump the "Last reviewed" date in the header. Commit and push both.

A `Stop` hook (`.claude/hooks/session-doc-reminder.sh`, wired in `.claude/settings.json`) blocks the end of any session that changed repo files without touching the Confluence page. It fires once per session and is a backstop, not the mechanism — do the update because the page is the deliverable, not because the hook asked.

This same handoff mechanism is mirrored for Cursor (any model) at [.cursor/rules/amo-session-handoff.mdc](.cursor/rules/amo-session-handoff.mdc), which points to the same `SESSION_LOG.md`. Keep both this file and that one in sync if operational facts change — they intentionally duplicate the facts below so either tool works standalone.

## Operational facts

- **Deploy:** production runs on a DigitalOcean droplet (`165.22.35.75`, `/opt/amo-dashboard`, **4 vCPU / 8GB RAM / 160GB disk** — resized 2026-07-21 from 1 vCPU/1GB for the full-history facility backfill; OCR workers auto-scale via `os.cpu_count()` capped at 4, and `run_facility_tick.sh` runs `--max-concurrent 4` sized for this box). The Node server (`dist/index.cjs`, port 5000) is **managed by PM2** under the app name `amo-dashboard` — PM2 auto-restarts it if killed, so never manually `kill` + relaunch (that fights PM2). Deploy sequence: `git pull` → `npm run build` → `pm2 restart amo-dashboard` (build BEFORE restart, or PM2 relaunches the old bundle). `git pull` alone does NOT update the live site. Don't kill Python backfill processes when restarting. Long-running one-off scripts (e.g. `normalize.py`) must be started with `nohup ... &` + `disown` — a dropped SSH session kills plain foreground runs (add `-u` to python for unbuffered log output). **After re-running `normalize.py`, also `pm2 restart amo-dashboard`** (or `POST /api/cache/bust` from a logged-in session) — API responses are cached in-memory for 7 days (`server/cache.ts`), so the dashboard keeps serving pre-rebuild data until the cache is cleared.
- **Droplet access:** key auth is installed (`~/.ssh/id_ed25519`, passphrase held in the macOS Keychain via `ssh-add --apple-use-keychain`). Claude ran the full 2026-08-06 deploy — pull, build, `pm2 restart`, apply approvals, `normalize.py`, cache-clear restart — directly over SSH at the user's instruction. This supersedes the earlier rule that all droplet actions were manual. Still ask before acting on production: it is live, and the user decides when to deploy.
- **LLM provider is OpenAI** (`gpt-4.1-nano` by default) for `collector/extract_pdfs.py` and `collector/enrich_entities.py` — not Claude/Anthropic.
- **Counties:** Miami-Dade and **Broward are both LIVE** — Broward went end-to-end on 2026-08-10 (index → images → extraction → normalization → county-scoped UI). Its analytical coverage is still thin (539 of 42,559 documents extracted); see SESSION_LOG and ROLLBACK. Broward needs no scraping: its index comes from a public SFTP feed (`BCFTP.Broward.org:22`, `crpublic`/`crpublic`) via `collector/broward_collect.py`, which requires **`paramiko`** in the venv. Run `collector/migrate_add_county.py` before it. Document images come from the same feed via `collector/broward_images.py` — **time-critical: the feed retains only ~10 days, and missed images are unrecoverable from the free channel** (`collector/run_broward_daily.sh` is the cron wrapper). The two counties share one DB and are distinguished by a `county` column; `assignments.cfn` stays globally unique only because Miami-Dade CFNs always contain `R` and Broward instrument numbers are always pure digits — `collector/tests/check_county_isolation.py` asserts it.
- **GitHub workflow:** every agreed-on code change should be committed and pushed to `origin/main` once confirmed.
- Local dev DB (`AMO_DB_PATH=./miami_dade_amo.db`) can lag production significantly — check actual row/date coverage before assuming it's current.
